## Profile source comparison

The checked-in JSON and the former Kotlin production mirror agreed on profile IDs, boot modes, artifact IDs, disk sizes, initialization kinds, recovery SSH, and most minimum requirements. The mirror nevertheless omitted three Ubuntu qualification checks present in canonical JSON:

- `virtio-block`;
- `virtio-net`;
- `serial-console`.

The JSON also carries fixed compatibility fields that the mirror did not read from data: architecture `aarch64`, machine family `virt`, acceleration `tcg`, PCI device transport, primary network `slirp`, recovery guest port `22`, recovery bind `loopback`, and raw data-disk format. The packaged parser now validates those values instead of silently discarding alternatives.

## Artifact manifest inventory

Before F01, the same active manifest was interpreted independently by:

- controller upload publication and moved-payload recovery;
- public HTTPS import publication, installed checks, and interrupted-publication cleanup;
- Host API image listing;
- QEMU runtime artifact resolution.

Each parser checked a different subset of fields or payload properties. F01 now uses one strict adapter requiring the exact versioned fields, digest, size, immutable relative path, payload size, and root containment. Expensive digest verification remains explicit at trust boundaries rather than hidden in every listing call.

## Implemented boundary

- Android assets are generated from the exact checked-in profile JSON, schema, and rendered trusted guest-init sources.
- The APK verifier compares every required profile, schema, index, and guest-init asset byte-for-byte with canonical source output.
- `AndroidPackagedProfileCatalog` reads only the three qualified profiles from bounded immutable APK assets and maps them to the existing typed domain model.
- Fixed Android/QEMU compatibility constraints are validated before mutable disk or QEMU effects.
- `AndroidQemuProfileStorage` no longer constructs complete profiles or maps profile IDs to boot artifacts.
- Guest vendor data is selected through the packaged profile rather than profile-specific Kotlin branching.
- `ArtifactManifestStore` owns active-manifest writing, parsing, listing, payload resolution, installed checks, cleanup decisions, and root containment.
- Controller upload, public HTTPS import, Host API image listing, and QEMU runtime consumption use that adapter.
- Legacy direct files plus `.sha256` metadata remain isolated to the pinned Podroid qualification assets.
- Static CI guards prohibit reintroducing complete profile construction in runtime storage or direct active-manifest interpretation outside the adapter.

## Next-phase decision

The post-F01 preflight work should be split by failure domain rather than activated as the original broad H02/H03 packets:

1. **Guest boot qualification** — canonical Ubuntu profile, pinned artifacts, UEFI/QMP, NoCloud, key-only loopback SSH, restart, and secret-residue inspection. This is the next active uncertainty.
2. **Guest mesh qualification** — one-use Headscale enrollment, distinct guest identity, tailnet SSH, `tailscaled` restart, Headscale interruption, and recovery. Queue until guest boot qualification passes.
3. **Stateless emulator harness** — deterministic API 36 create/boot/install/execute/collect/destroy. Queue until the guest path is qualified or a lifecycle blocker makes it higher priority.
4. **Emulator lifecycle scenarios** — Activity, Service, Room, enrollment, permission, and API behavior through real ports with release-surface exclusion. Queue behind a proven harness.

Only guest boot qualification should enter the next active DAG. The other three remain queued hypotheses and must receive their own phase-start review before implementation.
