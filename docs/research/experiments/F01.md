## Profile source comparison

### Common fields mirrored correctly

The Kotlin mirror uses the same profile IDs, versions, boot artifact IDs, system-disk artifact IDs/formats, writable-layer values, data-disk defaults, initialization kind/path, metadata path, recovery SSH defaults, health mode, minimum memory/storage, and parent ID represented by the typed domain model.

The JSON also carries fixed compatibility fields that the current Kotlin mirror does not read from data: architecture `aarch64`, machine family `virt`, acceleration `tcg`, PCI device transport, primary network `slirp`, recovery guest port `22`, recovery bind `loopback`, and raw data-disk format. The packaged parser must validate these values rather than silently discard arbitrary alternatives.

### Concrete drift

- `ubuntu-2404-arm64-uefi/profile.json` requires qualification checks `uefi`, `virtio-block`, `virtio-net`, `serial-console`, `cloud-init`, and `openssh`.
- The Kotlin mirror currently constructs only `uefi`, `cloud-init`, and `openssh`.
- Alpine and K3s represented fields currently match their checked-in JSON, but remain duplicated and can diverge later.

### Packaging gap

`node-shell` currently has no generated profile asset source. The application packages the pinned Podroid runtime assets but not the three canonical profile JSON files as one verified namespaced profile bundle. K3s has a separate hand-copied asset, which is another source of drift from the checked-in guest-init tree.

## Artifact manifest inventory

### Producers

1. `AndroidArtifactUploadStore.publishLocked` writes the active manifest after moving a verified staged payload into `versions/<artifact>/<digest>/payload`.
2. `AndroidHostMutations.publishVerifiedDownload` writes the same layout for the hardened public HTTPS importer.

### Consumers and recovery readers

1. `AndroidArtifactUploadStore.published` validates an already active artifact.
2. `AndroidHostResourceQueries.images` lists active images.
3. `AndroidHostMutations.isInstalled` detects an already imported image.
4. `AndroidHostMutations.cleanupInterruptedPublications` decides whether a digest-addressed payload is orphaned.
5. `AndroidQemuProfileStorage.artifactFile` resolves a manifest path for runtime consumption.
6. `AndroidQemuProfileStorage.expectedDigest` reads the manifest digest for runtime verification.

### Current inconsistency

- Upload and public-import checks validate most or all manifest fields independently.
- Image listing has its own exact-field parser.
- Runtime resolution reads only `relativePath` and `sha256`; it does not require the exact field set, version, declared size, or declared immutable path shape.
- Cleanup independently interprets a subset.

## Selected implementation boundary

### Packaged profile catalog

A narrow Android adapter will:

- load only `nodehost/profiles/<id>/profile.json` for the three allowed IDs;
- bound asset size;
- require exact JSON field sets and `apiVersion`/`kind`/metadata version;
- validate fixed Android/QEMU compatibility values;
- resolve artifact IDs through the artifact repository;
- construct the existing typed `VmProfile` domain model;
- confirm a declared parent profile exists before returning a child;
- expose no raw QEMU/kernel arguments.

Build-time `make validate` remains the full JSON Schema validation. Runtime parsing repeats the fail-closed contract required before effects without adding a JSON Schema library to the APK.

### Profile asset bundle

Gradle will generate a namespaced asset tree from the exact checked-in files:

```text
nodehost/profiles/<profile-id>/profile.json
nodehost/profiles/guest-init/**
```

The package verifier will compare APK bytes with source bytes for all three profile JSON files and required guest-init sources.

### Artifact repository/manifest contract

One adapter will own:

- exact manifest parsing and validation;
- root-contained immutable payload resolution;
- active-manifest writing;
- already-installed checks;
- image listing;
- runtime ArtifactRef resolution;
- manifest-aware cleanup decisions.

Built-in Podroid assets may continue to use their existing bare-file plus `.sha256` representation during this phase, but only through the same repository adapter. That explicit fallback cannot be selected when a manifest exists and cannot relax manifest validation.

## Out of scope

- true qcow2 backing files;
- changing the domain workload boundary;
- replacing Kotlin/Compose/Hilt, Ktor, Python controller, Room, or libtailscale;
- runtime JSON Schema dependencies;
- H02/H03 implementation;
- physical gate promotion;
- USB/AOA.
