# H02A — Canonical Ubuntu guest boot qualification

## Status

**IMPLEMENTATION IN PROGRESS.** H02A is the sole authorised task in phase `guest-boot-2`. The production-aligned preparation boundary is implemented on `agent/H02A-canonical-host-qemu`; no host-QEMU boot or qualification evidence is claimed yet.

## Question

Can the canonical Ubuntu profile, rendered vendor-data, pinned cloud image, and explicitly recorded host AAVMF inputs boot repeatably under Linux host QEMU, reach real QMP `running`, complete NoCloud, accept only key-based loopback SSH, and recover after guest and QEMU restart without introducing guest-mesh bootstrap secrets?

## Phase-start baseline

The prior `make qemu-lab-e2e` flow did not answer the question:

- `lab/qemu/scripts/prepare.sh` wrote a parallel hand-authored cloud-init document instead of using the canonical rendered vendor-data;
- it downloaded Ubuntu `current` and mutated the lock during preparation instead of consuming a previously pinned immutable identity;
- it used a qcow2 backing-file overlay while the production profile truthfully names `copied-writable`;
- it discovered and copied host firmware but did not record the selected paths, digests, sizes, and package/tool facts before launch;
- `start.sh` carried a second hard-coded QEMU profile in shell;
- it proved only one initial boot/SSH smoke, not guest reboot, complete QEMU stop/start, authentication-negative cases, or bounded forbidden-material scanning.

## Implemented preparation result

The first bounded implementation slice closes the configuration/source-of-truth gaps without claiming runtime success:

- `profiles/locks/images.lock.json` pins the immutable Ubuntu 24.04 ARM64 release dated `20260725` at exactly 618,098,176 bytes with SHA-256 `2eaec7286c49fdea713dddabcf5012cafa7097a658e916acb48f4bc5fdc8e419`;
- normal preparation validates and consumes that lock without rewriting it;
- lock updates require an explicit immutable release date through `tools/profiles/pin-ubuntu-image.sh YYYYMMDD`;
- `h02a-prepare.py` validates the exact canonical profile shape and qualification checks;
- canonical vendor-data is rendered with the production renderer;
- test-only user-data adds only an ephemeral SSH public key, strict SSH policy, and `/var/lib/nodehost/h02a-ready`; it does not create `bootstrap.env`, install mesh software, or carry bootstrap/callback credentials;
- the system disk is an independent copied-writable qcow2 with no backing file;
- the profile's 8 GiB raw data disk is attached separately;
- selected AAVMF source paths, digests, exact sizes, package facts, tool facts, source commit/dirty state, profile/vendor-data identities, and the closed QEMU command are recorded in `preflight.json` before launch;
- `start.sh` executes `qemu-command.json` instead of maintaining a second QEMU configuration.

Offline tests validate the immutable lock, profile contract, test-only user-data boundary, closed command shape, no-backing-file policy, loopback-only forwarding, and shell entry points without downloading the image or requiring QEMU.

## Remaining runtime qualification

The next implementation slice must add and then actually execute:

1. real QMP greeting/capability negotiation and `query-status == running`;
2. `cloud-init status --wait` and readiness-marker verification;
3. key-only SSH plus negative password, keyboard-interactive, and root-login checks;
4. a clean guest reboot with a changed boot ID;
5. a complete QEMU stop/start with a second changed boot ID;
6. bounded scans of generated seed inputs and guest state for forbidden bootstrap/mesh material;
7. final redacted `host-qemu` evidence and exact cleanup verification.

## Evidence class

`host-qemu`; never Android, emulator, or physical evidence.

Required evidence fields include:

- source commit and dirty state;
- canonical profile SHA-256;
- canonical rendered vendor-data SHA-256;
- Ubuntu lock URL, SHA-256, and size;
- selected AAVMF code/vars paths, SHA-256 values, and sizes;
- QEMU, firmware/package, cloud-init, and SSH versions where observable;
- resolved profile/QEMU compatibility facts;
- QMP status;
- cloud-init completion;
- password, keyboard-interactive, and root-login policy;
- key-only loopback SSH result;
- guest reboot and QEMU stop/start results;
- bounded scan showing H02A introduced no auth key, bootstrap token, callback capability, bootstrap environment, or secret-shaped canary;
- cleanup result;
- `androidHardwareValidated: false`;
- `physicalGateEligible: false`;
- `guestMeshValidated: false`.

## Boundary decision

H02A uses canonical vendor-data as NoCloud vendor-data plus a clearly test-only user-data layer for the ephemeral SSH key and readiness marker. It does not create the bootstrap environment that activates the canonical mesh/bootstrap service.

Headscale, Tailscale enrollment, one-use secret redemption/erasure, callback readiness, tailnet SSH, coordination recovery, Android process-death/runtime-ownership work, AVF, emulator work, and physical validation are excluded.
