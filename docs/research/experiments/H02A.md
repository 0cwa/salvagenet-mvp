## Question

Can the canonical Ubuntu profile, rendered vendor-data, pinned cloud image, and explicitly recorded host AAVMF inputs boot repeatably under Linux host QEMU, reach real QMP `running`, complete NoCloud, accept only key-based loopback SSH, and recover after guest and QEMU restart without introducing guest-mesh bootstrap secrets?

## Phase-start baseline

The original `make qemu-lab-e2e` flow did not answer the question:

- it wrote a parallel hand-authored cloud-init document instead of canonical rendered vendor-data;
- it downloaded Ubuntu `current` and mutated the lock during preparation;
- it used a qcow2 backing-file overlay despite the `copied-writable` profile contract;
- it did not record exact firmware or launch identities before QEMU;
- `start.sh` carried a second hard-coded QEMU profile;
- it proved only one permissive SSH smoke and wrote best-effort evidence.

## Merged preparation result

PR #80 established the production-aligned boundary:

- immutable Ubuntu 24.04 ARM64 release `20260725`, exactly 618,098,176 bytes, SHA-256 `2eaec7286c49fdea713dddabcf5012cafa7097a658e916acb48f4bc5fdc8e419`;
- canonical profile validation and production vendor-data rendering;
- deterministic two-part test MIME data: a `users`-only cloud-config part mirrors canonical `nodeadmin` and installs the ephemeral key during the config stage, while a final shell part adds qualification-only sudo, SSH hardening, and readiness without overriding vendor package, `write_files`, or `runcmd` lists;
- an independent copied-writable qcow2 system disk and separate 8 GiB raw data disk;
- matched AAVMF code/vars selection and byte verification;
- exact source, profile, vendor-data, image, firmware, tool, and normalized QEMU-command facts in `preflight.json`;
- launch solely from the recorded `qemu-command.json`;
- state confinement under the repository's ignored `.local` tree.

## Runtime implementation under review

The current branch adds a closed, evidence-producing three-stage qualification:

1. **Initial boot** — QMP `running`, cloud-init done, readiness marker, key-only SSH, effective SSH policy, guest tool facts, and bounded secret scan.
2. **Guest reboot** — SSH interruption and return, a distinct boot ID, the same SSH host key, and a complete second stage record.
3. **Complete QEMU restart** — guest poweroff, confirmed QEMU exit, launch from the recorded command, a third distinct boot ID, the same SSH host key, and a complete third stage record.

The implementation also adds:

- strict QMP greeting/capability negotiation, request IDs, event skipping, response bounds, and a two-command allowlist;
- explicit refusal to signal stale PIDs whose `/proc` command identity is not the recorded H02A QEMU process;
- failed password-only, keyboard-interactive-only, and root-key SSH client probes alongside `sshd -T` policy checks;
- a transparent qualification-only `/etc/sudoers.d/90-nodehost-h02a` rule, validated by `visudo`, so the locked-password `nodeadmin` user can execute bounded privileged checks and lifecycle commands through `sudo -n`;
- preflight and per-stage evidence that records and requires that noninteractive qualification capability;
- bounded scans of canonical seed inputs, cloud-init state/logs, temporary state, process environments, and mesh residue;
- strict imported-scan schema, scope, statistics, and pass/finding consistency;
- mandatory serial/stdout/stderr snapshots for all three stages;
- evidence creation only from clean-source preflight plus complete stage records;
- final cleanup that retains only the reverified immutable image and bounded evidence directory;
- removal of the obsolete one-boot best-effort reporter.

The passwordless sudo rule is laboratory-only. It is created by the H02A final shell part, not the canonical vendor-data, and is not a production guest-profile or guest-mesh contract. It introduces no reusable password, bootstrap token, callback capability, or mesh key.

## Real host findings resolved before qualification

- Packaged AAVMF aliases may be symlinks; they are accepted only when their resolved regular files remain confined under `/usr/share/AAVMF`, and both requested and resolved identities are recorded.
- Ubuntu host QEMU may not ship the optional `efi-virtio.rom`; the recorded PCI virtio-net argument explicitly uses `romfile=` without changing the profile transport.
- TCG boot reached cloud-init network/config after the original 360-second SSH bound; the lab now uses a measured 900-second SSH readiness bound.
- Canonical package/final work can continue beyond that point. The ephemeral key therefore moves to a `users`-only config-stage MIME part, while the host waits separately for cloud-init final completion before requiring final hardening/readiness.

## Boundary decision

H02A uses canonical vendor-data plus deterministic two-part test MIME data. Its `users`-only cloud-config part mirrors canonical `nodeadmin` and installs the ephemeral SSH key early enough for the host to observe cloud-init; its final shell part adds qualification-only sudo, SSH hardening, and readiness. It does not create the bootstrap environment that activates the canonical mesh/bootstrap service.

Headscale, Tailscale enrollment, one-use secret redemption/erasure, callback readiness, tailnet SSH, coordination recovery, Android process-death/runtime-ownership work, AVF, emulator work, physical validation, and acceptance-gate changes remain excluded.
