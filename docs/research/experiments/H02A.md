# H02A — Canonical Ubuntu guest boot qualification

## Status

**QUEUED FOR REACTIVATION.** The prior phase-start review completed after F01 merged, but no host-QEMU implementation or qualification result is recorded. H02A is paused for the bounded WEB04 roadmap/agent foundation and must receive a fresh phase-start review afterward.

## Question

Can the canonical Ubuntu profile, rendered vendor-data, pinned cloud image, and explicitly recorded host AAVMF inputs boot repeatably under Linux host QEMU, reach real QMP `running`, complete NoCloud, accept only key-based loopback SSH, and recover after guest and QEMU restart without introducing guest-mesh bootstrap secrets?

## Baseline finding

The current `make qemu-lab-e2e` flow does not yet answer the question:

- `lab/qemu/scripts/prepare.sh` writes a parallel hand-authored cloud-init document instead of using the canonical rendered vendor-data;
- it downloads Ubuntu `current` and mutates the lock during preparation instead of consuming a previously pinned immutable identity;
- it discovers and copies host firmware but does not record the selected paths, digests, sizes, and package/tool facts in evidence;
- it proves only one initial boot/SSH smoke, not guest reboot, complete QEMU stop/start, or bounded forbidden-material scanning.

This is the exact implementation gap H02A must close when it is reactivated.

## Evidence class

`host-qemu`; never Android, emulator, or physical evidence.

Required evidence fields include:

- source commit and dirty state;
- canonical profile SHA-256;
- canonical rendered vendor-data SHA-256;
- Ubuntu lock URL, SHA-256, and size;
- selected AAVMF code/vars paths, SHA-256 values, and sizes;
- QEMU, firmware/package, cloud-init, and SSH versions where observable;
- resolved profile/QEMU compatibility facts;
- QMP status;
- cloud-init completion;
- password, keyboard-interactive, and root-login policy;
- key-only loopback SSH result;
- guest reboot and QEMU stop/start results;
- bounded scan showing H02A introduced no auth key, bootstrap token, callback capability, bootstrap environment, or secret-shaped canary;
- cleanup result;
- `androidHardwareValidated: false`;
- `physicalGateEligible: false`;
- `guestMeshValidated: false`.

## Boundary decision

H02A uses canonical vendor-data as NoCloud vendor-data plus a clearly test-only user-data layer for the ephemeral SSH key and readiness marker. It does not create the bootstrap environment that activates the canonical mesh/bootstrap service.

Headscale, Tailscale enrollment, one-use secret redemption/erasure, callback readiness, tailnet SSH, and coordination recovery are excluded. Those belong to H02B and cannot be activated until H02A passes its phase-end review.

Before reactivation, inspect the live roadmap/index and any merged device-lab safety work. Preserve the product/evidence boundary and revise only where current implementation changed the real prerequisite.
