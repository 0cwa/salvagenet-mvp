## Question

Can the canonical Ubuntu profile, rendered vendor-data, pinned cloud image, and explicitly recorded host AAVMF inputs boot repeatably under Linux host QEMU, reach real QMP `running`, complete NoCloud, accept only key-based loopback SSH, and recover after guest and QEMU restart without introducing guest-mesh bootstrap secrets?

## Phase-start baseline

- it wrote a parallel hand-authored cloud-init document instead of canonical rendered vendor-data;
- it downloaded Ubuntu `current` and mutated the lock during preparation;
- it used a qcow2 backing-file overlay despite the `copied-writable` profile contract;
- it did not record exact firmware or launch identities before QEMU;
- `start.sh` carried a second hard-coded QEMU profile;
- it proved only one permissive SSH smoke and wrote best-effort evidence.

## Runtime merge candidate

The branch implements a closed, evidence-producing three-stage qualification:

1. **Initial boot** — QMP `running`, cloud-init done, readiness marker, key-only SSH, effective SSH policy, guest tool facts, and bounded secret scan.
2. **Guest reboot** — a successful nonblocking reboot request, polling until the boot ID changes, the same SSH host key, and a complete second stage record.
3. **Complete QEMU restart** — guest poweroff, confirmed QEMU exit while the recorded PID is still available, launch from the recorded command, a third distinct boot ID, the same SSH host key, and a complete third stage record.

The implementation also adds:

- strict QMP greeting/capability negotiation, request IDs, event skipping, response bounds, and a two-command allowlist;
- explicit refusal to signal stale PIDs whose `/proc` command identity is not the recorded H02A QEMU process;
- canonical base-10 SSH-port validation that rejects leading-zero/octal-like input;
- measured password-only, keyboard-interactive-only, root-key, key-only, and noninteractive-sudo checks rather than unconditional authentication flags;
- a test-only, non-authenticating `NP` password sentinel that keeps `nodeadmin` eligible for public-key access while canonical `ssh_pwauth: false`, the final SSH drop-in, and explicit negative client probes prove password access remains unavailable;
- a transparent qualification-only `/etc/sudoers.d/90-nodehost-h02a` rule, validated by `visudo`, so `nodeadmin` can execute bounded privileged checks and lifecycle commands through `sudo -n`;
- preflight and per-stage evidence that records and requires the qualification account-password and sudo capabilities;
- bounded scans of canonical seed inputs, cloud-init state/logs, temporary state, process environments, and mesh residue, including direct stdin-execution coverage and named walked/process scopes;
- strict imported-scan schema, scope, statistics, and pass/finding consistency;
- mandatory serial/stdout/stderr snapshots for all three stages;
- evidence creation only from clean-source preflight plus complete stage records, with non-object evidence rejected through the normal bounded error path;
- final cleanup that proves QEMU quiescence before PID removal, independently reconfines deletion below repository `.local`, and retains only the reverified immutable image and bounded evidence directory;
- removal of the obsolete one-boot best-effort reporter.

The account sentinel and passwordless sudo rule are laboratory-only. They are created by H02A test data, not canonical vendor-data, and are not production guest-profile or guest-mesh contracts. `NP` is neither a reusable password nor a password hash. Neither mechanism introduces a bootstrap token, callback capability, or mesh key.

## Real host findings resolved before qualification

- Packaged AAVMF aliases may be symlinks; they are accepted only when their resolved regular files remain confined under `/usr/share/AAVMF`, and both requested and resolved identities are recorded.
- Ubuntu host QEMU may not ship the optional `efi-virtio.rom`; the recorded PCI virtio-net argument explicitly uses `romfile=` without changing the profile transport.
- TCG boot reached cloud-init network/config after the original 360-second SSH bound; the lab uses a measured 900-second SSH readiness bound and a separate 1,800-second cloud-init-final bound.
- Canonical package/final work can continue beyond initial SSH availability. The ephemeral key therefore lives in a `users`-only config-stage MIME part, while the host waits separately for cloud-init final completion before requiring final hardening/readiness.
- The exact-head serial diagnostic proved SSH and the ephemeral key were already working. Cloud-init instead deadlocked after `systemctl enable --now nodehost-bootstrap.service`: the command ran inside `cloud-final.service`, while the unit was ordered `After=cloud-final.service`. Canonical vendor-data now enables the unit and queues `systemctl start --no-block`, and preparation rejects the deadlocking form.
- Exact offline disk inspection proved that cloud-init installed the expected public key at `/home/nodeadmin/.ssh/authorized_keys` with mode `0600` and UID/GID `1000`, while `/etc/shadow` still began with `!`. Ubuntu OpenSSH rejects such a locked account even for public-key authentication. The disposable H02A overlay therefore uses the non-authenticating `NP` sentinel and records that mode explicitly.
- A single failed SSH probe is not a reboot boundary; the laboratory requires a valid changed boot ID before the second stage.
- Cleanup cannot infer quiescence after deleting the PID record; it checks the still-recorded process identity before removing runtime state.
