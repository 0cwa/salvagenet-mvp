# H01 experiment record

## Status

**Resolved and merge ready.** The selected protocol is implemented on `agent/H01-artifact-upload`; GitHub Actions run `30509824017` passed the complete static, JVM, Android, lint, guest, packaging, signature, 16 KiB alignment, and candidate-artifact workflow.

The experiment closes the software design and recovery questions below. It does not claim physical-device or real multi-gigabyte transfer evidence.

## Selected MVP semantics

- Controller-to-host uploads are authenticated resources separate from public HTTPS imports.
- Uploads are sequential, resumable, and exact-replay idempotent.
- Chunks are limited to 1 MiB and carry their own SHA-256.
- Progress metadata and payload bytes are fsynced and stored under app-private staging paths.
- Completion verifies the whole expected size and digest before publishing the existing digest-addressed payload and active-manifest layout.
- Cancellation never deletes a completed/active artifact.
- The controller derives deterministic upload idempotency from artifact ID, digest, and size, and resumes from host-reported committed bytes.
- The hardened public URL importer and its SSRF/DNS-rebinding policy remain unchanged.

## Findings and resolution

### Publication recovery — resolved

Payload movement and active-manifest publication form a recoverable transaction. Recovery runs before stale collection. If a full verified payload reached `versions/<artifact>/<digest>/payload` but the active manifest is absent, restart verifies the immutable payload and finishes manifest publication before the upload can be cancelled as stale.

### Bounded staging lifecycle — resolved

Only `OPEN` records count against the open-upload limit. Stale open records are cancelled and their staging payload is reclaimed; stale terminal records are removed under a bounded directory-entry budget. A cancelled idempotent request can be safely replaced by a new upload record.

### Resource semantics — resolved

- Unknown upload IDs are `404 Not Found`.
- Offset gaps, partial overlap, conflicting replay, completion-before-full-size, terminal-state mutation, open-capacity exhaustion, and idempotency-key reuse are `409 Conflict`.
- Malformed IDs, invalid digests, negative offsets, media-type violations, and oversized chunks remain `400 Bad Request`.

### Persisted metadata — resolved

Recovery requires the exact metadata field set and supported version. Unknown or future versions fail closed.

### Existing publication checks — resolved

An active manifest must have exactly the expected version, digest, size, and immutable relative payload path. Upload creation recognizes the digest-addressed immutable payload through that exact manifest plus file size and does not rehash a large published payload.

### Shared publication arbitration — resolved

Resumable upload and public HTTPS import share one process-local `ArtifactPublicationCoordinator`. Payload/manifest publication is serialized; the later serialized completion becomes the active manifest. Digest-addressed versions remain immutable and may coexist.

### Existing API/security invariants — restored

Review of the first implementation found regressions in list bounds, diagnostics validation, URI validation, apply conflict mapping, and recovery-session admission. H01 restores the pre-existing fail-closed behavior and adds regression coverage before introducing upload behavior.

### Controller integrity — resolved

The client hashes the local file, streams bounded chunks, resumes only from host progress, verifies every upload response and final image identity, checks that the local file did not change after hashing, and redacts reflected capability/idempotency values.

## Deferred beyond H01

Parallel/out-of-order chunk upload, TUF, OCI transport, distributed upload mirrors, content-defined chunking, multi-controller cooperative transfer, physical storage-pressure testing, and process death during a real multi-gigabyte transfer are not required for the one-phone MVP and remain separate evidence or future tasks.
